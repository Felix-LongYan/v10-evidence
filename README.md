# V10 evidence

## What this repository is

A repository of an existing strategy-game prototype, its rule testbed, and its historical run evidence, assembled so that the claims in my application materials can be checked. It provides a local constraint-checking entry point that needs no API key and no network access.

## What each file is, and what it does and does not prove

The copies below keep their original contents. This assembly adds no experiments and changes no earlier conclusion.

- `src/caocao_deepseek.py` — the original V10 source. This is the "before" object of the four checks; its behaviour is left unchanged.
- `src/caocao_deepseek_v11.py` — the patched version, generated from the file above by the accompanying `tools/v10_patch.py`. This is the "after" object of the same four checks. It was generated by pointing the patch script's `SRC` at the copy in this repository in memory and passing `--out`; neither the patch script nor the original file was edited.
- `src/demo_script.py` — the original demo helper script. It preserves how the demo was driven; it is not independent evidence that the demo succeeded, and the offline entry point does not run it.
- `src/requirements.txt` — the original dependency declaration, kept as-is. It does not pin complete dependency versions; the offline command below needs only the Python standard library and does not install these.
- `tools/v10_patch.py` — the original patch-generation script, recording how the patch was produced. **It still defaults to an old path on the author's desktop and will not run with default arguments on another machine.** The generated patched version is included here.
- `tools/constraint_demo.py` — the original constraint-checking script. The offline entry point calls it with `--both --path <repo>/src`, running the same four checks against both versions: whether a numeric change is bounded to ±12; whether the string `"false"` is refused as an event trigger; whether an illegal value leaves a half-updated state; and whether an out-of-range attempt is recorded. The fourth check is an instrument capability, not a correctness property.
- `evidence/demo_run.log` — the output log of a recorded demonstration, 77 lines. It supports checking what was recorded at the time; it cannot reconstruct the original API responses.
- `evidence/constraint_demo.log` — the original constraint demonstration log, preserving the three records made at the time. It is kept separate from the four-check comparison generated here.
- `evidence/constraint_verify.log` — the four-check comparison output, written or overwritten when `reproduce.sh` runs. It contains the actual results and totals: 0 of 4 for the original, 4 of 4 for the patched version.
- `evidence/timeleak-runs/run_*.txt` — the run texts used by the anachronism candidate scan.
- `evidence/timeleak-runs/hits.csv` — the keyword candidate hits. **A candidate scan cannot prove the absence of anachronisms.**
- `evidence/timeleak-runs/results.md` — the original summary, method and limits for that scan, kept as-is. It is not a new manual review.
- `testbed/env.py` — the rule environment, sample generation, and the oracle. It lets a reader check how the gold answer is computed from the rules; **it is not independent third-party verification of correctness.**
- `testbed/ask.py` — the original script that questions the model, scores it, and writes results. It lets a reader inspect how the earlier experiment was implemented. Running it by default calls the API; the offline entry point does not run it.
- `testbed/runs/*/results.csv` — the per-item records of each historical run. `run-20261015-1607/results.csv` is the main run checked here: 541 lines including the header, i.e. 540 data records. **The other historical runs are also kept in full**; the offline entry point prints each one's actual line count and does not merge them into the main run.
- `testbed/runs/*/summary.md` — the original summary for each historical run, keeping its own scope. The presence of a file, or its line count passing, is **not** re-verification of every metric in it.
- `reproduce.sh` — the offline verification entry point added here. It checks the syntax of both versions, runs the original constraint script, saves the output, and checks the line counts above. The wrapper collects only the four booleans the check script actually returns when computing the total; a missing check, an exception, or a mismatch exits non-zero. **It does not pre-fill any result.**
- `README.md` — this document: what the files are, and the limits of the evidence.

**Provenance.** The three original files in `src/`, the two existing logs, and `evidence/timeleak-runs/` come from the author's local project folder; `tools/` and `testbed/` come from the author's local working folder. The two existing logs were renamed to `demo_run.log` and `constraint_demo.log` on copying only; the source files were neither renamed nor moved.

## How to reproduce

Requires Python 3.10 or newer on macOS. Open a terminal in this repository and run one command:

```sh
./reproduce.sh
```

It prints, in order: the syntax check for both versions; the four constraint checks item by item, with 0 of 4 for the original and 4 of 4 for the patched version; the line count of each historical CSV (541 including the header for the main run); and the line count of the demo log (77). The constraint output is written to `evidence/constraint_verify.log`, overwriting that verification log on each run.

**No API key, network access or SDK installation is needed.** The original program imports `openai` at module level; the offline entry point supplies a placeholder module in the current Python process that satisfies the import only. Any attempt to construct an API client or open a socket raises and exits. The four checks execute only the original program's local state, event and logging functions — they use no model response. The syntax check does not run either program's main entry point and writes no bytecode cache.

What this command reproduces is four local behavioural checks, plus line-count checks on historical files. **It does not re-run the historical model experiments, the demo, or the anachronism scan.** A line-count check verifies file size only; it does not establish that the contents are genuine or that the metrics in them are correct.

## What this evidence does not prove

- **A single model.** The historical material covers one model configuration, with no cross-model comparison. It cannot be generalised into a claim about LLMs as a class.
- **No pinned snapshot.** The model service snapshot was not pinned and the dependency declaration does not fully lock versions. There is no guarantee that the service returns the same results at another time, and a temperature of 0 does not mean identical output on every call.
- **The oracle and the rules share one author.** The oracle is a rule function written by the same person who wrote the rules, with no independent third-party implementation to cross-check against. It cannot establish real-world causal validity or general causal reasoning ability.
- **Raw API responses were not retained.** There are no complete raw API responses or request metadata. The `raw_response` field in the CSVs is a truncated text fragment saved by the script, and the demo log is processed output. Neither can reconstruct the full response, the token usage, or the server-side version.
- **The checks are narrow.** 0 of 4 and 4 of 4 correspond only to these four specific check inputs. They do not show that every boundary input is handled correctly, that the program has no other defects, or that the patch improved the model's capability.
- **Historical records are not a re-run.** Keeping CSVs, summaries and logs is not the same as re-running a paid model experiment offline. Nor can a keyword candidate scan show that the anachronism risk is zero.
